3e — Motion

Three levels of ambition, running live. Same interactions, same tokens, different nerve.

You said you want to lean into this, so rather than write a duration table and call it a decision, here are the five interactions that carry the most motion in these apps, built at three intensities and looping side by side. One thing shapes all of them: Bindery and App A both poll. Rows repaint on their own every few seconds, so animation has to go big in the chrome — layers, navigation, state changes, feedback — and stay near zero in live data. Every tier below respects that; they differ in how much they do with the room that leaves.

Measured120–200ms · ease-out · fade and small travel · no stagger, no overshoot

What the brief signed off. Motion confirms, never performs.

Confident160–320ms · a soft spring on entrances · staggered lists · the tab pill travels

Motion explains where things came from. The recommendation if you want more without amending the brief.

Expressive200–460ms · real overshoot · choreographed sequences · counters roll · rows fly out

Genuinely characterful. Amends the "strongly restrained" slider in BRIEF.md — worth doing knowingly.

What ships Expressive everywhere except the menu family

Expressive for modal, toast, tab switch, list load and row dismissal. Confident for dropdown menus — and, by the same reasoning, for popovers and tooltips. A menu is opened dozens of times an hour; a choreographed entrance with staggered items is charming the tenth time and tiring the hundredth. A modal is occasional, so it can afford the theatre. What never animates the same list in all three tiers

NeverBecause
A table row whose content changed on a pollBindery and App A repoll lists. Animating a value that updates on its own turns a quiet screen into a slot machine. New rows may enter on first paint; a changed cell just changes.
Anything on a route change in a data viewFading a table on every navigation makes the app feel slower than it is, and it delays the thing the user came to read.
Text reflow, column widths, table layoutLayout animation is the most expensive kind and the least readable. Columns drop at a breakpoint; they do not slide.
The focus ringIt must appear on the same frame as the key press. A 140ms fade on focus is a 140ms lie about where you are.
Validation errors appearingAn error that animates in reads as decoration. It should already be there when the user looks.
Skeletons, beyond one slow shimmerA loading state that draws attention to itself competes with the content it is standing in for.

Reduced motion not a downgrade path — a supported mode

Every tier collapses to the same thing under prefers-reduced-motion: opacity only, 1ms, no transform. This page honours it too — if your system is set to reduce motion, every demo above is already still, and that is the correct rendering, not a broken one.

One constraint inherited from App D, which is out of scope as a product but got this right: entrances animate from an offset to the element's natural state, using animation-fill-mode: backwards — never forwards. A retained transform turns the wrapper into a containing block, which silently breaks every position: fixed overlay inside it. That bug costs an afternoon to find and one line to prevent.
Reduced motion is currently on in your system settings — the demos above are intentionally static.
