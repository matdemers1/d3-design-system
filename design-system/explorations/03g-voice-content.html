3g — Voice & content

Casing, dates, numbers, errors, empty states and button labels — decided from the copy that is already in the four apps.

Two things the audit found are worth stating up front. There are 31 bare toLocaleDateString() / toLocaleString() calls across the four apps and exactly one that passes options — so the same timestamp renders 8/12/2026 for you and 12/08/2026 for a colleague in London, inside a table where that difference changes the meaning. And the error strings sit in two incompatible registers: "Rate limit reached. Wait a moment and try again." is genuinely good, while "sender_device_id required for group decryption" is a parameter name that reached a user. Every example below is a real string from the codebase.

Sentence case for everything a person reads: buttons, form labels, headings, navigation, dialog titles, menu items, empty states, tooltips. The only capitals are the first letter and proper nouns — GitHub, Claude, Acme Corp, Bindery. The one exception is not a casing rule at all: the 11px uppercase micro-label used for table headers and section labels is a typographic treatment applied via CSS text-transform, so the underlying string stays sentence case and stays translatable. Never type an uppercase string into the source.

The month is always a word. 12 Aug 2026 and Aug 12, 2026 are both unambiguous; 8/12/2026 is not, and which one a user sees today depends on their OS. The rule is to pin the options and let the locale choose the order — { day: 'numeric', month: 'short', year: 'numeric' } — never to call toLocaleDateString() bare and never to hard-code a locale.

Every relative time carries the absolute one in its title. "2 hours ago" is easier to read and impossible to cite; the tooltip and the detail view give the timestamp. And relative time stops at a week — "47 days ago" is arithmetic the reader has to undo.

The audit found 23 references to 1024 and four different toFixed() precisions — 0, 1, 2 and 4 — across the apps. Byte formatting is written once, in the system, and imported. Currency has no rule yet because none of the four apps handles money; when one does, it gets Intl.NumberFormat with the currency code shown for anything that is not the user's own.

Three rules. Never show an internal identifier — a parameter name, a class name, a key type. Never blame the user ("you entered an invalid…"); describe the state. And always give the next action where one exists, as a real control rather than a sentence telling someone to go and find it. An error with no next step is a dead end with punctuation.

An empty state has three parts and the first two are never optional. A heading naming what is absent, one line of context, and an action if one genuinely exists. "No items" is not an empty state — it is a status code. Note also the distinction the rewrites make: nothing exists yet and nothing matched your filter are different situations with different next steps, and the four apps currently render both as "No items".

Button labels

NeverInsteadWhy
ConfirmDismiss 3 itemsA destructive button names what it destroys, and how many.
OKGot it“OK” answers a question nobody asked.
Yes / NoDelete library / Keep libraryNever Yes/No on a destructive dialog — the verb is the safety.
SubmitSend feedback“Submit” describes the form, not the outcome.
SaveSave changesSay what is saved when the object is not obvious.
CancelCancelAlways “Cancel”. Never “Nevermind”, “Go back”, “Close”.
A button says what will happen, from the user's side. Verb first, object when the object is not obvious from context. A destructive confirmation names the object and the count — Dismiss 3 items, not Confirm — because the count is the last chance to notice you selected the wrong rows. Cancel is always "Cancel": it is the one label in the system that never gets rewritten, because a user scanning for the way out should not have to read.

Words this system does not use

Oops / Whoops / Uh ohSomething failed and the interface is being cute about it. Say what happened.
Simply, just, easyIf it were simple the user would not be reading an instruction. It only ever tells someone their difficulty is their fault.
Please (in errors and labels)Politeness padding in an interface reads as delay. Keep it for genuine imposition.
Are you sure?Almost always. Say what will happen instead: "This deletes 3 items and cannot be undone."
InvalidA judgement, not a description. Say what was expected.
Error occurredEvery error occurred. Say which one.
Loading… as a lone stateUse a skeleton of the thing being loaded. A spinner over a blank page hides how long it will take.
