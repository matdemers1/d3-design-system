Phase 3 · Foundations

3c — Spacing & layout

One base unit, twelve steps, four breakpoints, and a shell that finally behaves the same in all four apps.

Spacing is the least interesting decision here and the shell is the most. Bindery collapses its sidebar at 1024px and remembers the state; App C drawers at 768px; App A at 600px; App B has no responsive behaviour at all and simply breaks below about 900px. Four apps, four answers, four sidebar widths — 224, 240, 256 and 260. This picks one of each, and the one it picks for collapse behaviour is Bindery’s, because Bindery already solved it properly.

Base unit and scale 4px base · twelve steps · no compact mode (D-007)

2px0.5×hairline gaps — chip dot to label, icon to its own edge
4px1×tight icon gap, checkbox to label
6px1.5×gap inside a button, chip padding-y
8px2×standard small gap — toolbar items, form row
12px3×table cell padding-y, stacked form fields
16px4×table cell padding-x, small card padding
20px5×card padding, modal padding
24px6×section gap, page padding at sm
32px8×page padding at lg, gap between major regions
40px10×space above a page footer action
48px12×table row height, large section separation
64px16×collapsed sidebar width, page-level rhythm
Twelve steps, and 6px is the only one off the 4px grid. It exists because a 4px gap inside a button is too tight and 8px is too loose at 13px type — Tailwind ships it as 1.5 for the same reason. The audit found Bindery using 17 spacing steps, App D 18, and App C 17 raw pixel values including 5, 7 and 14. This is twelve, and anything not on it is a lint error (Phase 6).

Breakpoints four, not six — the apps use xl once and 2xl never

Three of the four apps already use them, they map to real device classes, and inventing different numbers would buy migration churn and nothing else. 2xl is dropped — the four apps reference it zero times and xl once. A breakpoint nobody uses is a state somebody still has to test.

The collapse behaviour is Bindery's, adopted wholesale. A 240px column above lg, collapsible to 64px by user choice and remembered in localStorage, and an off-canvas drawer with a scrim below it. Bindery's own comment explains why a sidebar at all — eleven destinations do not fit in a top bar — and that reasoning holds for App A's fourteen. App B gains responsive behaviour it has never had.
Columns drop, they do not shrink. Below md the table loses Date; below sm it loses Submitter. Description and Status stay at every width, because a triage row that cannot be identified or acted on is not a row. Squeezing seven columns into 420px is how you get a table nobody can read on either device.

TokenValueUsed for

--container-prose65chhelp text, trust pages, anything read as prose

--container-wide1280pxdashboards and table pages — the cap that stops a 4K monitor producing 3,000px rows
Data pages cap at 1280px. The audit found no max-width on any table page in any app, which means on a 4K monitor a Bindery archive row is three thousand pixels wide and the eye has to travel the whole way to connect a filename to its date. The cap is the point of the token.
