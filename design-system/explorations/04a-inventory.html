Phase 4a · Inventory

What to build, and what to refuse to build.

Thirty-eight component concepts, counted across the four apps. Twenty of them ship.

Every number here is measured, not estimated: each concept was matched against the source of all four apps and counted by instance and by app. One caveat matters more than the counts. This measures what exists, not what is needed — Toast scores two uses, and App A alone has 107 error-surface call sites rendering as inline alerts. Demand data tells you what duplication costs today; it cannot tell you what is missing. Both are used below.

What the count turned up

All four of App B's dialogs are inaccessible. AddMemberDialog, NewDMDialog, SafetyNumberDialog and ProfileModal have no role="dialog", no aria-modal, no Escape handler and no focus management — a keyboard user tabs straight out of the dialog into the page behind it. Bindery's Modal.tsx does all four correctly; App A gets them free from MUI. This is the Radix decision (D-009) justifying itself before a line is written.

Bindery has 42 bare title= attributes doing the job of a tooltip. A native title attribute does not appear on keyboard focus, cannot be styled, and is invisible to touch. That is 42 pieces of guidance most users never see.

App C duplicates within itself. Five badge families (badge, priority-badge, stage-badge, memory-type-badge, memory-count-badge) and three dropdown families (status-dropdown, inline-dropdown, enhance-menu) in one 1,469-line stylesheet. Not every duplication problem is between apps.

The v1, and the line it draws

v1 is everything inside the content area. v2 is the frame.

That is the whole scoping principle, and it is what makes the cut list coherent rather than arbitrary. Buttons, fields, cards, badges, modals, tooltips and empty states are things that appear within a page, they are identical across all four apps, and getting them wrong is cheap to fix. The shell, the drawer, the auth screens and the settings layout are the page frame — they carry routing, auth state and per-app navigation, and unifying them first would mean the first thing the system ever does is the riskiest thing it will ever do.

Twenty components. 1197 of 1456 measured instances — 82%. The brief asked for roughly 60% of the value; the data says twenty components buy considerably more than that, because the distribution is brutally top-heavy. Button alone is 345 instances — 24% of everything, in one component.

What gets cut, and why eighteen refusals

Divider
41 uses · 3 app(s)
It is a 1px border in the border token. Wrapping a CSS property in a React component is ceremony, not reuse.
Breadcrumb
0 uses · 0 app(s)
Zero uses in four apps. Adding it would invent a navigation pattern none of these products has.
Radio
1 uses · 1 app(s)
One use, in Bindery. A Select covers the same job until a second app disagrees.
Switch / toggle
3 uses · 1 app(s)
Three uses, App C only — and its .view-toggle is really a segmented control, not a switch.
Command palette
4 uses · 1 app(s)
The most complex component on this list, with exactly one consumer. Bindery's works. Building it for one app is how a design system becomes a hobby.
Pagination
10 uses · 1 app(s)
App A only, and it is a cursor-based “Load more” — which is a Button.
Wizard / stepper
17 uses · 1 app(s)
Seventeen uses, all App A. A large T2 pattern serving one app; revisit if a second one needs it.
Data table (full)
32 uses · 1 app(s)
Sorting, selection and bulk actions exist only in App A's inbox. The v1 primitives make its cells consistent without the system owning its behaviour.
Toast
2 uses · 1 app(s)
Deferred, but flagged: App A has 107 error-surface call sites rendering as inline alerts. Alert covers v1; Toast is the first thing into v2.
Dropdown menu
8 uses · 2 app(s)
Eight uses across two apps — but App C has three dropdown families internally. Low volume, real duplication. First into v2 alongside Toast.
Popover
26 uses · 2 app(s)
Bindery's “panels” are layout regions, not popovers. Reclassifying them is a Bindery decision, not a system one.
Accordion
10 uses · 3 app(s)
Ten uses. <details> is adequate until a second app needs controlled state.
Table
21 uses · 3 app(s)
The v1 Card, Badge and Skeleton make a table look right. Owning table markup means owning column sizing, sticky headers and virtualisation — that is a v2 project.
Drawer
8 uses · 3 app(s)
Belongs with the shell, and the shell is v2.
Filter bar
31 uses · 3 app(s)
A composition of Input, Select and Button — all in v1. It becomes a component once the composition repeats identically, not before.
App shell + nav
7 uses · 4 app(s)
Four shells is the single largest duplication in the audit, and the single riskiest thing to unify first. It is v2 by design, not by neglect.
Auth screens
17 uses · 4 app(s)
Four login/register pairs, but they differ in real ways — App B bootstraps encryption keys at signup. Compose from v1 primitives first.
Settings layout
21 uses · 3 app(s)
A page layout, not a component. Waits for the shell.
Two of these cuts are deferrals with a date, not refusals. Toast and Dropdown menu are the first two components of v2 — Toast because 107 inline error alerts is a real gap the audit found and Alert only half-covers it, and Dropdown menu because App C is maintaining three of them. Everything else on this list waits for a second app to ask.

What happens next

Phase 4b is the specs, and no code is written until they are approved. Each one covers: anatomy · variants · sizes · every state (default, hover, focus-visible, active, disabled, loading, error, read-only, empty) · accessibility contract (role, keyboard map, ARIA, focus management) · responsive behaviour · content guidance · do/don't pairs.

They come in four batches so they can be approved without reading twenty specs at once: Batch 1 Button, IconButton, Link, Badge, Spinner, Skeleton, Avatar · Batch 2 Input, Textarea, Select, Checkbox, Label, FormField · Batch 3 Card, Modal, Tooltip, Tabs, Alert · Batch 4 EmptyState, PageHeader.
