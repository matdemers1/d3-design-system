# Working on `@d3cloud/ui`

The system exists because five apps had **176 distinct colour values, 19 type sizes
and 170 button recipes**, and nothing was stopping the count going up. So the
first thing to understand is that most of this document is enforced by two
scripts rather than by goodwill.

```bash
npm run verify      # tokens → usage → typecheck → tests → build → dist check
```

## The two gates

**`check-tokens.mjs`** — the JSON sources in `design-system/tokens/` and the
stylesheets built from them must agree, and the copy vendored into this package
must match the original. Values are compared, not names, because the naming rule
is per-group and bespoke while the values are literal on both sides.

The stylesheets are **hand-maintained, not generated**. Their comments carry the
reasoning behind the numbers, which is most of their value and which no
generator can reproduce. For eleven phases they claimed to be generated by a
script that was never committed; the check is what makes the claim true in the
only way that matters — a value cannot drift.

To add a token: edit the JSON, edit the built CSS, run `npm run check:tokens`.
If a token is deliberately not a custom property — a breakpoint, a package name,
a value only ever composed into a shorthand — mark it in the JSON and say why:

```json
"$extensions": { "d3": { "emit": false, "why": "Tailwind owns breakpoints; they are media queries." } }
```

**`check-usage.mjs`** — bans the five habits that produced the audit: raw hex,
raw Tailwind palette classes, off-scale values on a scale the system owns,
primitive `--p-*` tokens, and shadows. Run it against any app:

```bash
node design-system/scripts/check-usage.mjs src
```

It deliberately says nothing about `grid-cols-[1fr_22rem]` or `max-h-[80vh]` —
a layout template and a viewport height are not scales the system has an opinion
about, and a gate that reports 73 things when 42 are real is one people learn to
skip.

Genuinely exceptional code carries `d3-allow: <reason>` on the line above. The
reason is required. Bindery has 13 of them and every one names something the
system does not cover — a PIN field spaced so digits can be counted, a highlight
sized to a word rather than to a control, a brand lockup.

## Adding a component

1. **Find it in the audit first.** The non-goal that matters most is components
   nobody needs. `SegmentedControl` was built for five real call sites; a
   letter-spacing scale was *not* built, because four uses across two patterns is
   not enough evidence to invent one.
2. **Decide the semantics before the pixels.** `SegmentedControl` is a
   `radiogroup` and not a `Tabs` variant, because these change what one region
   shows and have no panel to own — and a `tablist` with no tabpanel is a lie
   told to a screen reader.
3. **Write the story and the test with the component.** Every story is swept by
   axe automatically; the glob picks up new files, so a component with stories
   is a component with an accessibility check.
4. **Render it and measure it.** See below — this is the one that keeps failing.

## Measure the thing, don't trust the suite

Three defects in a row shipped past a green suite, and the pattern never varied:

| What passed | What was actually true |
|---|---|
| 297 tests | `Input` was 36px and `Button` 34px — the library shipped no `box-sizing` reset |
| Motion tests | jsdom returns `''` for computed animation, so they asserted on empty strings |
| 326 tests | The built package shipped every class name and **none of its CSS** |

The suite is good at semantics — roles, names, wiring, state — and blind to
geometry. Before claiming a component works, open it and read its numbers out of
the browser: heights, positions, computed colour. The spinner shipped at
**1.29:1 against the surface** for an afternoon because it was checked in a
review page rather than at 14px.

## Versioning

Semver, and the public surface is what `src/index.ts` exports plus the token
names. The CSS class names (`.d3-btn`, `.d3-seg`) are **not** public — they are
an implementation detail apps must not select on.

- **patch** — a fix that changes no API and no rendered geometry
- **minor** — a new component, a new optional prop, a new token
- **major** — a removed or renamed export, a changed default, a token whose
  meaning moves

Tag releases `v0.1.0`. Apps install from the tag; the `file:../../d3-ui` link is
for local development only and brings its own hazards (see
`bindery/web/vite.config.ts` for the two it has already caused).

## Deprecation

Nothing is removed in the release that deprecates it.

1. Mark it `@deprecated` in the TSDoc with the replacement named, and warn once
   in development.
2. Ship at least one minor release carrying both.
3. Remove in the next major, and say so in the changelog.

A prop that is dangerous rather than merely superseded is a different case:
remove the affordance instead of documenting the rule. `IconButton` has no
`danger` variant for exactly this reason.

## Health check, quarterly

Cheap to run, and each line exists because something went wrong once.

- [ ] `npm run verify` in the library, and `npm run lint` in every app that has
      adopted it
- [ ] `node design-system/scripts/check-usage.mjs src` in every app **including
      the ones not yet migrated** — the number should only ever fall
- [ ] Count the exemptions. A `d3-allow` that has been there a year is either a
      missing token or a rule that is wrong
- [ ] Read `DECISIONS.md` for anything marked open, and close or re-open it
- [ ] Check the tokens vendored into the library still match
      (`npm run check:tokens` does this, but run it after any token change)
- [ ] Open Storybook at 14px and in light mode. Both are where things break, and
      neither is where anyone looks
